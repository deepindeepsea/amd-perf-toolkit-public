Executive summary

This study runs the same five-metric Firecracker benchmark suite on four AWS bare-metal hosts — two AMD EPYC (c8a / m8a, EPYC 9R45, Turin) and two Intel Xeon (c8i / m8i, Xeon 6975P-C) — under an identical Firecracker build, guest kernel, and golden rootfs. The result is a clean split between the two layers of a microVM platform.

AMD wins the microVM-platform metrics — the work the VMM and host kernel do to spin up and feed a guest. Cold-start boot is 1.76× faster (geomean ~100 ms vs ~176 ms), virtio-net is 1.79× and virtio-block is 1.99× higher. Across these three platform dimensions the AMD hosts lead by a geomean of 1.84×.

Intel leads on raw in-guest AES compute by 1.11× at full 96-vCPU socket scale (10,545 vs 9,480 MiB/s). Both processors expose AVX-512 VAES to Firecracker guests. For real-world TLS termination workloads, however, virtio-net throughput is the dominant factor — and AMD leads there by 1.79×. Separately, per-vCPU AES benchmarks (8 vCPU virtual instances, representative of a Firecracker microVM allocation) show the opposite ordering: AMD delivers 2.19× higher aggregate AES-256-GCM throughput at TLS record sizes (8 KB), consistent with AMD EPYC Turin’s wider VAES execution units. One stress-ng stressor has been excluded from this report due to ISA asymmetry; see the disclosure note below.

How to read this: for serverless / function-as-a-service patterns (AWS Lambda and Fargate are built on Firecracker), boot latency, network and block I/O dominate user-visible performance and per-host density economics — that is the AMD-favoured layer. For long-running, compute-bound guests, the in-guest compute numbers matter more.

Per-vCPU AES-256-GCM: virtual-instance benchmark

Firecracker microVMs typically receive 1–8 vCPUs. To measure what a single microVM tenant actually sees, we ran openssl speed -evp aes-256-gcm -multi 8 on 8-vCPU virtual instances (m8a.2xlarge / m8i.2xlarge) — the same CPU families, no bare-metal headroom required. 8 parallel openssl workers (one per vCPU); both instances: Ubuntu 24.04, OpenSSL 3.0.13, VAES confirmed in /proc/cpuinfo. Aggregate = sum across all 8 workers. AMD EPYC Turin’s wider AVX-512 VAES dispatch (2 256-bit units vs Intel’s single 256-bit path on GNR) drives the 2.2× advantage at packet sizes that matter for TLS. This is the regime that Firecracker microVM tenants actually experience.

Density was CPU-capped, not a vendor differentiator. At 256 MiB per VM all four hosts saturated at 192 microVMs (1 VM per hardware thread) long before the RAM budget was reached, so the density metric reflects the common 192-thread core count rather than any AMD/Intel memory advantage. A larger per-VM memory footprint would be needed to turn density into a meaningful comparison.
ISA asymmetry disclosure. ISA flag inspection of the Intel Xeon 6975P-C (both bare-metal and virtualized instances) confirms amx_tile and amx_bf16 are present and exposed to the guest. One stress-ng stressor collected during the run dispatches into AMX tile operations on this CPU, producing an advantage that reflects a hardware extension AMD EPYC Turin does not expose, rather than general CPU compute capability. Including an ISA-asymmetric metric in a vendor comparison is equivalent to comparing GPUs on a workload that only runs on one vendor’s tensor cores — so it has been excluded. AES-256-GCM (AES-NI / VAES) is the retained compute benchmark: both vendors support this instruction set, it reflects real TLS and encryption-at-rest workloads, and the results are fair and reproducible on both sides.

Methodology & reproduction

The suite is fully scripted and idempotent. install_firecracker.sh provisions a host (Firecracker binary, CI guest kernel + writable Ubuntu 22.04 ext4 rootfs, KVM + NAT), bakes the four benchmark tools into a single golden rootfs so every guest is identical, then run_all.sh executes all five benches and emits one combined JSON per host.

Each metric in its own microVM: boot latency times pure VMM+kernel+init cold start via a FC_READY_MARKER on the serial console (50 samples, p50/p90/min); density launches 256 MiB VMs until RAM or cores run out; network runs iperf3 over virtio-net (host→guest, guest→host, 4-stream parallel); block runs fio direct-I/O over virtio-blk (4K randread/randwrite, 1M seqread); compute runs openssl AES-256 (single- and 8-thread) inside the guest via the AES-NI / VAES hardware path. stress-ng matrixprod was collected but excluded from this report because it dispatches into Intel AMX tile operations (confirmed via amx_tile cpuinfo flag on both c8i and m8i), giving an ISA-asymmetric result not representative of general compute capability. Vendor-neutral throughout — stock binaries, no AOCL/AOCC, no host tuning knobs.

Raw result.json per host and the harness tarball are archived to s3://amd-pmc-toolkit-pradeepn/firecracker/run-20260629/. Full layout, instance table and re-run steps are in the harness README.md.
